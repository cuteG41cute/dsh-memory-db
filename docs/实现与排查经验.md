# dsh-memory-db 实现与排查经验

> 本文记录插件在真实使用中踩过的坑、验证过的做法与排查手段，供后续维护与同类插件开发参考。
> 面向读者：本插件的维护者、编写 DSH 常驻插件的开发者。

---

## 1. 架构要点（为什么这么设计）

| 设计点 | 原因 |
|---|---|
| **判定走 `inline`（默认），不用常驻子代理** | 子代理每次"结算"都会由 DSH runtime 生成一条**完成通知**注入父会话；通知到达**空闲**父会话会额外触发一次模型请求（见 §3）。通知唤醒的额外回合比判定本身更贵，因此默认不建子代理 |
| **注入内容落在消息尾部** | LLM 前缀缓存只认"从头逐字节连续"。尾部注入落在"本来就要未命中的区域"，边际成本≈0；插到历史中间会让其后整段失效 |
| **判定失败按"转向"兜底** | 漏注入（该给记忆却没给）的危害远大于多注入一次 |
| **关闭记忆库即释放分类器** | 避免子代理在界面堆积、避免失效对象被反复投递 |

## 2. 关键 API 契约与版本坑

### 2.1 `subagents.followup` → `sendMessage`（DSH 升级破坏性变更）

旧版：
```js
await subagents.followup(parent, childId, content, { source: { kind: 'coordinator', form: 'relay', senderSessionId }, signal })
```
新版（当前）：
```js
await subagents.sendMessage(sender, targetId, content, { signal })
```
`sendMessage` 自行推导消息归属，不再需要 `source`。**兼容写法**：

```js
if (typeof subagents.sendMessage === 'function') await subagents.sendMessage(agent, childId, content, { signal })
else if (typeof subagents.followup === 'function') await subagents.followup(agent, childId, content, { source, signal })
```
> 症状：日志出现 `subagents.followup is not a function`，B 通道全程降级。

### 2.2 `subagents` 的可用方法（当前版本）

`startContinuable` / `sendMessage` / `interrupt` / `drainContinuableDescendants` / `drainContinuableChildren` /
`listChildren` / `listDescendants` / `registerProvider` / `getProvider` / `list` / `start`
——**没有 `followup`**，也没有"删除子代理"的方法（释放用 `drainContinuableChildren(parent, ids)`，需要**在世的父 Agent**）。

### 2.3 子代理会话的识别（用于隔离）

`SessionHeader` 自带官方字段，**不要用 id 前缀猜测**：

```js
function isSubagentSession(session) {
  const h = session && session.header
  if (!h) return false
  if (h.origin === 'subagent') return true
  if (typeof h.delegationDepth === 'number' && h.delegationDepth > 0) return true
  return false
}
```
`SessionLogSnapshot.session` 也带同一 header，可对"只读快照"路径（如历史回填）做同样判断。

### 2.4 `reasoningEffort: 'off'` 可能被适配器拒绝

**症状**：`llm.stream()` 只返回一个 `finish` chunk、零文本：
```
classifier A empty: chunks=1 kinds={"finish":1}
```
**原因**：部分适配器不接受 `reasoningEffort: 'off'`，请求立即空结束。
**做法**：双次尝试（先带 `off` 降本，空则不带该参数重试），并记录 `finish reason` / `usage` 便于定位：

```js
const first = await streamOnce({ reasoningEffort: 'off' })
if (first.text) return first.text
debugLog('classifier A empty(off): kinds=' + ..., ' finish=' + first.finishReason)
const second = await streamOnce({})          // 不带 reasoningEffort
if (second.text) { debugLog('classifier A ok without reasoningEffort'); return second.text }
```
另：输出预算过小（如 200）也可能被 reasoning 或长 JSON 吃光 → 判定类调用取 **1024** 更稳。

### 2.5 `listChildren` 是"每个会话"的，不是"每个项目"

`listChildren(parentSessionId)` 按 `createdAt` 排序返回**该会话的直接子代理**。因此"每会话至多一个分类器"是正确粒度；跨会话共用一个分类器会混淆判定上下文。

### 2.6 工具输出 schema：`required` 必须放顶层

```js
// ❌ 被 DSH 的 assertSupportedJsonSchema 拒绝（插件树加载失败）
properties: { enabled: { type: 'boolean', required: true } }

// ✅
properties: { enabled: { type: 'boolean' }, ... },
required: ['enabled', 'project', 'count', 'results']
```

### 2.7 settings schema 的 `default()` 会遮蔽"未初始化"判断

`s.boolean().default(false)` 让 `settings.get(ns)` 永远返回 `false`，"用户没设置过"与"用户设了 false"无法区分 → 迁移/回退逻辑永不触发。
**做法**：不加 `default`（未写入时字段为 `undefined`）：

```js
export const schema = s.object({ defaultEnabled: s.boolean(), projects: s.dict(s.boolean()) })
// settings.get() 未写入 → { projects: {} }，defaultEnabled === undefined
```

### 2.8 静态插件客户端通道别用 settingsScope

`dsh-host-apiproxy` 对 `settings.describe` 有**硬编码命名空间白名单**，第三方命名空间不会暴露给配置客户端。
**做法**：Host 注册 `webServer` exact 路由 + 客户端 `fetch`（本插件的 `/dsh-memory-db/api`）。
另外：**进程重启不会刷新已打开的页面**——client bundle 更新后需要用户 `Ctrl+F5`。

## 3. 子代理完成通知：机制与污染

DSH 的 `dsh-subagent` README 明确：

> 每个**已结算的 Activation** 一条通知 …… **到达空闲父级会启动一次独立的模型请求**，到达繁忙父级则不会。
> 这条由 runtime 生成的通知与模型编写的父子消息相互独立。

通知形如（user-role 消息）：

```
Background subagent <child-id> finished and will do no further work unless you send it more.
Its closing message: {...}
```

### 污染链（真实缺陷）

1. 判定用的常驻子代理每轮完成 → 一条通知进入主会话；
2. 主 agent 空闲 → 被通知唤醒 → **额外产生一条 assistant 回复**（用户看到"没提问却额外作答"）；
3. 该回复落在**同一 turn 内**，覆盖了本回合已收集的真实答案 → 记忆库出现"问题与答案错配"，且真实答案丢失；
4. 脏数据在后续回合被当作历史记忆注入回来，形成自我传播。

### 判定：直接用内容特征识别通知

```js
const NOTICE_RE = /Background subagent [0-9a-fA-F-]{6,} (finished|was stopped|ran out of room|declined|failed)/
```

### 修复（双层）

1. **结构性**：分类器默认 `inline`，不创建子代理 → 不产生通知（根治）；
2. **防御性**（必须保留，因为功能性子代理同样会发通知）：
   - assistant 消息按 `data.turn === pending.turn` **严格归属**；
   - **通知出现后不再覆盖已有答案**（`if (!pending.noticeSeen || !pending.answer)`），仅当尚无答案才接受，避免真丢答案。

实测日志：
```
collect: subagent notice seen (turn 83) ; later assistants will not override an existing answer
collect skip: assistant after subagent notice (turn 83)
collected pair: ... turn=83        ← 收集到的是通知之前的真答案 ✅
```

## 4. 数据正确性另两条规则

### 4.1 注入时排除当前会话自己的条目

本会话历史本来就在上下文里，再注入一遍纯属浪费 token。做法：`hits.filter(h => h.sessionId !== 当前会话id)`，并统计 `同会话过滤N` 便于观察。

### 4.2 turn 编号可能错位（收集顺序导致的偏移）

真实案例：用户 turn=5 提的问题，其回答被记录在 turn=6 之下。修复时不能假设"库中 turn 号 = 会话日志 turn 号"，需以**回答内容**为准做归位。

## 5. 排查手册

### 5.1 日志位置

`debug.log` 写在插件当前的"日志根目录"，其解析顺序：**当前活跃会话所属项目** → 第一个开启的项目。
（早期版本固定写在"第一个开启的项目"，曾导致日志落到 `backup` 项目里，排查时找不到。）

### 5.2 会话日志是多帧 zstd，`zstdDecompressSync` 只解第一帧

**症状**：解压一个 345KB 的 `session.v3.jsonl.zstd` 只得到 214 字符（会话头）。

**做法**：按 zstd magic number 切帧、逐帧解压再拼接：

```js
const MAGIC = Buffer.from([0x28, 0xb5, 0x2f, 0xfd])
function decodeMultiFrame(file) {
  const buf = fs.readFileSync(file)
  const offsets = []
  for (let i = 0, idx; (idx = buf.indexOf(MAGIC, i)) >= 0; i = idx + 4) offsets.push(idx)
  const parts = []
  for (let k = 0; k < offsets.length; k++) {
    const start = offsets[k]
    const end = k + 1 < offsets.length ? offsets[k + 1] : buf.length
    try { parts.push(zlib.zstdDecompressSync(buf.slice(start, end)).toString('utf8')) }
    catch (e) { /* magic 出现在数据内部时与下一帧合并重试 */ }
  }
  return parts.join('')
}
```
用途：从日志**重建真实问答对**、恢复被污染的历史数据（本项目 `fix-tainted-pairs.js` 即基于此）。

### 5.3 投影缓存里的"孤儿子代理条目"

**症状**：界面上出现大量"会话记录暂不可用"的子代理；用 `listChildren` / `drainContinuableChildren` 都清不掉。

**原因**：`~/.dsh/storages/session_projcache.json` 的 `tables.sessions[<id>].rows.subagent` 投影保留了**已删除会话**的分类器标记（label 为 `memory-db 话题分类器`）。这些条目的父会话不存在，而清理 API 都要求"在世的父 Agent" → 完全触及不到。

**判断孤儿**：该 id 在 `~/.dsh/sessions/<workspace>/` 下已无目录。

**清理（必须在 DSH 停止时做）**：进程运行中改文件会在退出时被内存快照回写覆盖。

```js
// 只删 label 匹配的条目，其余保留
const sub = v && v.rows && v.rows.subagent && v.rows.subagent.val
if (sub && sub.identity && sub.identity.label === 'memory-db 话题分类器') delete sessions[id]
```
配套：一个"等待进程退出"的守护脚本（轮询投影缓存文件，稳定 90 秒后判定 DSH 已退出再清理）比"让用户手动跑脚本"体验更好——注意 DSH 关闭后 agent 本身也没了，无法再接收指令。

### 5.4 快速状态自查

```powershell
# 开关 / 预算 / 判定统计 / 分类模式
# 由 agent 调用 memory_admin(action="status")，或：
Invoke-RestMethod http://127.0.0.1:3080/dsh-memory-db/api -Method POST -ContentType application/json -Body '{"method":"get-default","args":{}}'
# 管理页项目总览
(Invoke-WebRequest http://127.0.0.1:3080/memory-db-admin/api/projects).Content
# 日志
Get-Content "<项目>\.dsh\memory-db\debug.log" -Tail 30
```

`status` 应关注的字段：`模式=inline`（不再建子代理）、`开关实际来源`、`同会话过滤N`、`最近判定`、`最近注入`。

## 7. 上下文预算修正（v0.6.1）

### 7.1 症状

长会话（历史事件多、且已发生过 compaction）里：

- `memory_admin status` 显示 `已用≈963720 可用=0`、`标准注入上限=0`，注入等于被永久关闭；
- 但判定照常，`shift/recall` 回合仍会注入一次——注入块只有标题+尾注，**0 条记忆**（典型长度 ~149 字符），污染上下文。

### 7.2 根因

`computeBudgets` 里的"已用"来自 `estimateUsedTokens`：它遍历**整份会话事件日志**，把
`user/message`、`assistant/message` 的全部文本块累加。日志里包含：

1. 已被 compaction 压缩掉的历史（压缩只改模型上下文，不改事件日志）；
2. `reasoning` 块（模型不回传，实际不占 prompt）；
3. 历史注入过的记忆块本身。

于是"已用"被估到接近窗口（本会话 963,720 / 1,000,000），`available = window − used − maxTokens − safety` 直接归零。
而 `buildStandardText` 在条目上限为 0 时仍返回 `head + tail`（非空），`buildInjection` 只判空串 → 空块被注入。

### 7.3 修复

1. **改用系统真实 usage**（`measureUsedTokens`）：
   - 从后往前找最近一条带 `usage` 的 `assistant/message`，`prompt = inputTokens + cacheReadTokens + cacheWriteTokens`；
   - 再补上该条消息及其后新增消息的估算增量（该条 assistant 的正文属于"下一次请求"，必须加上）；
   - 没有 usage（适配器未返回）时回退事件日志估算，并且 `estimateMessageTokens` 只统计非 `reasoning` 块。
   - 实测：真实 114,694 vs 旧估算 963,720（约 8 倍差）。
2. **压缩前置**（`ensureRoom`，替代原来的 `maybeCompact`）：
   - `available < 窗口×20%` 时先 `compaction.compactNow(agent, signal)` 腾空间，再注入；
   - 同一项目 60s 内不重复压缩（避免反复重排历史击穿前缀缓存）；
   - 压缩后拿不到新 usage，按"内容预算"假设历史已收缩，重算 `available/contentCap/injectCap` 再注入。
3. **空注入守卫**：
   - `buildInjection`：`injectCap <= 0` 直接返回 `null`；
   - `buildStandardText`：一条原文、也没有摘要时返回 `null`。

### 7.4 验证

- `status` 的"已用"应显示 `已用≈115000(真实usage)` 量级，`可用`恢复到窗口的 ~76%；
- `debug.log` 出现 `compactNow to make room: available=... -> ...` 才代表压缩分支被触发（正常会话不该出现）；
- 注入块应包含真实条目，不再出现只有标题的空块。

## 8. dsh 0.2.x 兼容清单（静态插件 v0.6.x）

对外部 issue（dsh 0.2.1-rc.5，`ctx.settings.register is not a function`）的处理记录：

### 8.1 设置 API（dsh-settings ≥ 0.1.7-rc.2 移除 `register()` / `get()`）

- 启动时做能力检测（`typeof settings.register === 'function'` 等），不再无条件调用；
- settings 不可用 → 开关状态落到 `<DSH_HOME>/dsh-memory-db-switches.json`（跨版本稳定），检索/注入/收集功能不受影响；
- `mutate(ns, ops)` 只在 settings 可用（即 0.1.x，ns=`memory-db` 正是注册名）时调用；0.2.x 走文件，不会触发 `No configurable plugin entry "memory-db"`；
- **未做**：`static Config`。因此 0.2.x 的「设置 → 插件」里没有本插件表单（这一点与 issue 的验收项 4 不同），开关入口仍是顶部开关、管理页、`memory_admin` 工具。

### 8.2 `Session` 没有 `.events`（0.2.x）

统一适配器 `sessionEvents(session)`：优先 `session.snapshotEvents()`，回退旧 `session.events`（Map/数组）。已替换 6 处：

`lastInjectedText`、`estimateUsedTokens`（现为 `measureUsedTokens`）、`completedRounds`、`pendingUserRounds`、`hasPreviousUser`、`primeLiveSessions`（最后这处是 issue 清单之外的漏网，0.6.1 补上）。

注意：`sessionQuery.readSession()` 返回的是快照对象（`snap.events` 数组），与 Session 不是同一套接口，保持原样。

### 8.3 尚未在真实 0.2.x 上验证的部分

本机对照环境是 dsh 0.1.5-rc.2，以下只在 0.1.x 实测过，0.2.x 需要按启动日志确认：

- `compaction.compactNow(agent, signal)`（腾空间压缩）
- `webServer` 路由注册与客户端 `/dsh-memory-db/api` 通道
- `subagents.sendMessage` / 分类器子代理结算通知
- `sessionQuery.readSession().events`（脏分类器体检、旧数据回填）

### 8.4 会话格式 v4 的 source 形态（0.6.2）

**症状**：dsh 0.2.1-rc.5 上注入时报
`SessionFormatError: format v4 message requires a producer-owned source kind`，
记忆召回与工况提示都写不进会话。

**原因**：v4 在 Session 采纳消息前校验 `source.kind`，明确拒绝 v3 的
`{ kind: 'plugin', plugin: '<name>' }`。迁移器 `producerKind()` 对第三方插件的映射是
`` `plugin:${plugin}` ``，并删掉 `plugin` 字段。

**改法**（`lib/index.js`）：

```js
const PLUGIN = 'memory-db'
const PLUGIN_KIND = 'plugin:' + PLUGIN   // v4 producer-owned kind

// 写（4 处）：memoryHead / chat 工况 / task 工况 / pre-step 召回
source: { kind: PLUGIN_KIND, form: 'recall' }   // 或 form: 'mode'

// 读（3 处）：lastInjectedText、mode 探测、already 判重
m.source.kind === PLUGIN_KIND
```

0.1.x 没有这条校验；本机 0.1.5 的 Chat 客户端把非 `source.kind === 'user'` 的消息
一律渲染成「上下文注入」行（`contextProvenance()` 的 default 分支，label 取 kind），
所以新形态在 0.1.5 上仍然显示为注入行，只是标签从 `memory-db` 变成 `plugin:memory-db`。

**附加问题（0.6.0 已修）**：`static/package.json` 曾带 UTF-8 BOM，0.2.1 解析依赖声明失败会
直接把整个插件行禁用（`disabling profile plugin row ... Unexpected token '﻿'`）。
0.6.1 起仓库内已是无 BOM 的 UTF-8；发布前可自查：

```bash
head -c 3 static/package.json | od -c    # 不应出现 357 273 277
```

### 8.5 多实例部署（0.6.3）

同一台机器可能同时跑多个实例（例如 3080 旧实例 + 3081 新实例），每个实例有独立的
`DSH_HOME`、`sessions`、`settings.yaml`，但**项目目录是共享的**。插件侧的区分方式：

| 资源 | 是否按实例隔离 | 说明 |
|---|---|---|
| 管理页 URL | 是 | `adminUrl()` 取 `webServer.host` + `webServer.port`（`0` 时是 OS 分配的端口），不再写死 3080；`memory_admin status`、系统提示里的链接、`open-admin` 的浏览器打开都用它 |
| debug.log | 否（按项目共享） | 每行加了 `[p<port>]` 前缀，多实例写同一项目时可区分来源 |
| 开关状态 | 是 | 按 `DSH_HOME` 落盘（`settings.yaml` 或 `dsh-memory-db-switches.json`），实例之间互不影响 |
| 记忆数据 `memory.json` | 否（按项目共享） | `queueSave` 是整文件覆盖，两个实例服务同一项目时是 last-write-wins——可能丢条目。暂未做合并/加锁 |
| 会话 / 分类器子代理 | 是 | 各实例的 `sessions` 目录独立 |

多实例使用建议：

- 同一项目同一时间只让一个实例开启记忆库（另一个实例关掉），避免两边同时写 `memory.json`；
- 或让不同实例服务不同项目目录，各写各的 `.dsh/memory-db/`；
- 如果想要"多实例共享记忆 + 并发安全"，需要后续做写入合并（按 key 取并集 + 删除墓碑），属于独立改造。

## 9. 密钥脱敏（0.6.4）

### 9.1 为什么要做

对话里贴的 token 会被收集成问答对（`question` 字段），进而：

- 落盘进 `memory.json`；
- 被 FTS 索引、`verdicts.json`、`classify-ctx.json` 各存一份；
- 之后某次 `recall` 注入时再原样发给模型。

本项目历史上出现过两次（`memory.json.bak-token-redact` 就是上次手工清理的产物）。

### 9.2 做法

`redactSecrets(text)` 把匹配到的 token 替换成 `[REDACTED]`：

```
github_pat_[A-Za-z0-9_]{20,}
gh[pousr]_[A-Za-z0-9]{30,}
sk-[A-Za-z0-9_-]{20,}
AKIA[0-9A-Z]{16}
xox[baprs]-[A-Za-z0-9-]{10,}
```

接入点（入库 + 注入 + 落盘）：

| 位置 | 作用 |
|---|---|
| `recordPair` | 自动收集的问答入库前脱敏 |
| `addManagedEntry` | 管理页手工添加时脱敏 |
| `buildInjection` | 注入前再兜一次（覆盖旧数据） |
| `queueSave` / `queueSaveVerdicts` / `queueSaveClassifyCtx` | 落盘序列化时兜底 |

注意：已存在于事件日志/会话文件里的原文不会被改写（zstd 压缩、属于会话事实），发现泄漏时仍需手工清理数据文件并**轮换 token**。

### 9.3 何时生效

静态插件改代码必须重启 DSH 才加载；重启后新入库、新注入、新落盘都会脱敏。

## 10. 作为 bundle 注册到「插件」页面（0.6.5）

### 10.1 为什么手工插入的行不出现在插件页

dsh 0.2.x 的「插件」页（sidebar Plugins / `dsh-client-ui-plugin-manager`）管理的是 **profile 里声明的 bundle**（`dsh.profile.bundles` + `package.json` 依赖），不是 Loader 里的任意行。旧安装方式是在 `cordis.patch.yml` 里手写 `- insert:`，插件能跑，但页面里看不到。

### 10.2 做法

1. 包内声明 bundle 元数据：

   ```json
   "dsh": {
     "bundle": { "patch": "./cordis.patch.yml" },
     "client": { ... }
   }
   ```

   并在 `exports` 里暴露 `"./cordis.patch.yml"`。

2. 包内 `cordis.patch.yml` 写行（与原来 profile 里那条一致）：

   ```yaml
   - insert:
       - id: dsh-memory-db
         name: dsh-memory-db
         inject: [tools]
   ```

3. profile 的 `package.json`：

   ```json
   "dependencies": { "dsh-memory-db": "link:<包目录>" },
   "dsh": { "profile": { "bundles": [ ..., "dsh-memory-db" ] } }
   ```

4. **删掉 profile 的 `cordis.patch.yml` 里旧的手工 `- insert:` 行**。两条同时存在会**重复挂载**同一个 id（实测 `composeEntries` 不报错，但会得到两条 `dsh-memory-db` 行）。

### 10.3 离线验证（不重启也能确认）

```js
import { loadProfileDirectory, composeEntries } from '@deepseek-ai/dsh-app-boot'
const p = loadProfileDirectory('dsh', profileDir, installAnchor)
const rows = composeEntries([p.layers.flatMap(l => l.patches), p.patches])
console.log(rows.filter(r => r.id === 'dsh-memory-db'))   // 应恰好一条
```

`p.skippedBundles` 会列出被跳过的 bundle（不兼容/解析不到），据此判断是否漏装。

### 10.4 效果

- 插件页「已安装插件」出现 `dsh-memory-db`，带版本、组件列表和启停开关；
- 关闭 = 从 `dsh.profile.bundles` 移除 → 行消失、插件卸载（重启生效）；开启则反之；
- 组件行的细粒度开关可能显示 `readOnlyReason: unaddressable`（行来自 bundle patch 而不是 profile patch），属正常。
